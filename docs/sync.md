# 局域网同步（readerx-sync）

> 状态：**已接入 App**。本文件说明它解决什么问题、怎么用、边界在哪，
> 以及 App 侧的接线方式（`src-tauri/src/sync/` 与 `src/lib/sync.ts`）。

目标：同一个 ReaderX 的两台设备（手机 + 桌面）在**同一局域网内直接互相同步**，
不需要云服务、不需要账号体系。引擎住在 `src-tauri/crates/readerx-sync`，
**不依赖 Tauri / GUI**，与 `readerx-source` / `readerx-log` 同样是可独立编译的 crate；
App 与 CLI 用同一份引擎代码、同一个数据目录（`<应用数据目录>/sync`）。

```text
cargo test -p readerx-sync                          # 单元 / 集成测试
cargo build -p readerx-sync --features cli          # 独立命令行运行器
```

---

## 1. 核心问题与结论

两台设备各自离线改数据，联网后互相推送。核心不是「谁的更新覆盖谁」，而是：

1. **先判断两次更新是否并发**（版本向量），再按数据类型语义合并；
2. 不能自动合并的**进冲突队列**，人/业务规则事后处理——**不静默丢数据**。

落地的组合是：

> **全局唯一 id + 操作日志 + 版本向量（判并发）+ HLC（排序与裁决）+
> 字段级合并 + 墓碑删除 + 冲突队列表 + 版本向量增量同步。**

各机制解决的具体毛病：

| 机制 | 不做会怎样 |
| --- | --- |
| ULID（`id`） | 两台设备各自新增记录时主键撞车 |
| 操作日志（`model::Operation`） | 只看最终值无法判断「改的时候看到了什么」，并发检测无从谈起 |
| 版本向量（`version`） | 只能靠时间戳猜先后，「并发」与「顺序」分不开 |
| HLC（`hlc`） | 设备时钟不准 / 回拨会让新写入被判成旧值而丢失 |
| 字段级合并（`merge`） | 甲改书名、乙改简介被当成冲突 |
| 冲突队列（`model::Conflict`） | 败方数据被覆盖后无处可查 |
| 墓碑（`model::Tombstone`） | 删除与并发更新无法比较，离线设备会把已删记录加回来 |
| op_id 去重 | 网络重试导致同一次修改被应用两次（计数器尤其致命） |
| 版本向量增量同步（`session`） | 每次全量传输；断点续传与中继都要额外记账 |

## 2. 数据模型

```text
Operation   追加型日志，同步与重放的唯一真相
  op_id / origin / seq            全局唯一 id + 来源设备与设备内序号
  hlc                             混合逻辑时钟（排序、LWW 裁决）
  entity_id / kind / field        作用对象
  op                              Create / Set / Unset / Increment / Add / Remove / Move / DeleteEntity / RestoreEntity
  base                            作者写入时看到的实体版本 ← 判断并发的关键
  schema_ver                      写入时的 schema 版本

Entity      由操作重放出来的物化视图
  fields       字段名 → FieldState（Value / Multi / Frozen / Counter / Set / List）
  version      已并入的操作（origin → 最大序号）
  deleted      墓碑（hlc + 来源 + 删除者看到的版本）
  conflicted   待裁决字段

Conflict    冲突记录：原因、双方取值与时间、状态、裁决写下的操作 id
```

字段级状态与合并语义（schema 按实体类型声明，未声明字段一律 LWW）：

| `MergeKind` | 语义 | 并发时的结果 | 进冲突队列 |
| --- | --- | --- | --- |
| `Lww` | 单值，HLC 全序最后写入者胜出 | 选边，败方留档 | **是** |
| `LwwSilent` | 同 `Lww`，但**并发不记冲突** | 选边 | 否（见下） |
| `MultiValue` | 并发值全部保留（MV-Register） | 多值并存 | **是** |
| `Frozen` | 不可变（创建时写入一次） | 保留首次写入 | **是** |
| `Counter` | PN-Counter | 增量相加 | 否（语义确定） |
| `Set` | OR-Set（`add_wins` / `remove_wins`） | 按策略 | 否（语义确定） |
| `List` | 位置键（分数索引）有序列表 | 两个插入都保留，按 `(位置键, 元素 id)` 排序 | 仅「并发移动同一元素」记一条 |

「进冲突队列」**不等于合并失败**：数据先按确定语义合并（保证各副本收敛），
冲突记录把被覆盖的那一方原样留档，人能看见、能改回来。
**已被后续写入了结**的冲突会自动关闭（甲裁决后同步给乙，乙队列里的旧冲突随之消失）。

`LwwSilent` 只用在**阅读进度**这类「位置」数据上：两台设备各读到不同位置时，落后的一方
只是过时的位置，不是需要人裁决的内容 —— 若按普通 LWW 记冲突，第一次同步就会堆一屏
「保留哪个进度」，真正的数据冲突反而被淹没。取舍是明确的：这里放弃了「败方留档」，
代价可接受（位置本身没有信息量）。**不要拿它当「省事的 LWW」**，唯一键撞车等真冲突照记。

## 3. 同步流程

```text
本地写：生成 op（base = 实体当前版本）→ 先写 oplog.jsonl（fsync）→ 并进内存实体

收到远端 op：
  去重（op_id 见过就跳过）
    → schema 版本比本机新？进缓冲
    → 因果就绪？(entity.version ⊇ op.base) 否则进缓冲，等前序操作
    → 先写 oplog.jsonl（fsync；失败不改内存，可重推或重试缓冲）
    → merge（字段策略裁决 + 冲突留档）
    → 记进实体版本向量、推进本地 HLC、登记操作索引
```

一次同步（`session::sync_with`）是**双向**的：

```text
1. 拉：把我的版本向量发给对端 → 对端回「我有而你没有」的操作 → 合并（可能多轮）
2. 推：对端在应答里带上它的版本向量 → 我算出「它有而我没有」的操作 → 分批推送
3. 记录对端状态（地址 / 上次同步 / 对方已知版本）并落盘
```

用版本向量求差（而不是「已发送队列」）带来三个性质：**断点续传**（重启后差集重算）、
**中继**（A 的操作经 B 传到 C，C 的向量里有 A 的进度）、**幂等**（重复发也没事）。

因果就绪是 merge 的前提（`entity.version ⊇ op.base`）。有了它，
「对方有没有见过我这次写入」可以只看 `op.base` 里有没有我的 stamp，
于是「两次写入是否并发」不需要再存每字段的基线向量。局域网里操作乱序到达很常见，
所以缓冲是常规路径，不是异常路径。

## 4. 数据目录与文件

```text
<data_dir>/
  device.json      设备身份：设备 id、名称、群组 id、群组密钥（配对码）、本机拒绝接入的设备
  clock.json       HLC 进度（重启后不能从 0 重新计数）
  oplog.jsonl      操作日志：一行一条 Operation（追加 + fsync，唯一真相）
  entities.json    实体快照（物化视图）+ 快照覆盖到的日志行数
  conflicts.json   冲突队列
  deferred.json    因果缓冲
  peers.json       已知对端：地址、上次同步、我们认为对方已有的版本
  content/         **正文暂存区**：`content/<书实体 id>/<章节 cid 的 sha256>.json`
                   （对端刚发来、还没落地到书库的正文；落地后即删，见第 7.9 节）
  assets/          **资源暂存区**：`assets/<书实体 id>/<类别:名字 的 sha256>.json`
                   （对端刚发来的封面 / 插图字节；落地后即删，见第 7.10 节）
  .lock            目录锁（见下）
```

- **崩溃安全**：操作先落盘并 fsync；快照 / 冲突队列是「可重建的派生数据」，
  用「临时文件 + rename」原子替换。即使快照没来得及写，重启时会按
  `applied_ops` 与日志行数之差**重放尾部**。
- **格式版本**：每个文件带 `format`。读到比本程序新的版本会直接报错
  （`SyncError::Unsupported`），而不是按旧语义写坏新数据；旧版本走 `store::migrate`。
- **目录锁**：一个数据目录同一时刻只允许**一个写者**。第二个进程打开会被拒绝
  （`已被另一个进程（pid …）打开`），避免两边各有一份内存视图、互相覆盖快照而**静默分叉**。
  进程被强杀可能留下残留锁：Linux / Android 用 `/proc/<pid>` 判断存活并自动接管；
  其它平台保守拒绝，可用 `--force-unlock`（CLI）显式接管。
  **只读打开**（CLI 的 `status` / `ls` / `show` / `ops` / `conflicts`）不抢锁：
  同步服务在跑时依然可以查看数据（读快照 + 重放日志尾部即可得到最新视图）。
- **操作日志只增不减**：删掉旧操作会让落后的对端永远补不齐。
  需要控制体积时应引入「快照传输模式」（把实体状态作为基线发给对端），
  而不是清理日志；这一点当前**没有实现**，属于已知取舍。

## 5. 局域网传输

传输抽象是 `net::Transport`，同步语义只依赖它；当前实现两种：

- `net::TcpTransport`（真局域网）与 `net::PeerServer`（监听端）；
- `net::LoopbackTransport`（进程内直连：测试、同机两个数据目录自测）。

握手（HMAC-SHA256，密钥 = 群组密钥）：

```text
客户端 → Hello{protocol, group, device, name, knowledge, port_c, nonce_c, content}
服务端 → Hello{ok, protocol, group, device, name, nonce_s, code?, message?}  ← 校验协议 / 群组 / 信任名单
客户端 → Auth{proof = HMAC(secret, 文本(client))}
服务端 → Auth{ok, proof = HMAC(secret, 文本(server)), code?, message?}       ← 双向认证
之后每帧：Envelope{seq, mac}，MAC 覆盖 (seq ‖ 规范化 JSON)，seq 必须严格递增
```

`Hello` 里还自报**是否参与正文同步**（`content`，缺字段的旧对端按 `false`）：
同步协议当前为 `readerx-sync/2`，双方在 Hello 阶段严格校验版本，不一致即返回
`protocol_mismatch` 并断开，尚未进入鉴权或数据传输。版本也纳入 HMAC 认证文本。
v1 的正文能力标记不能保证支持资源传输，因此不再与 v2 混用；两台设备需升级到支持同一同步协议的版本。
协议版本独立于应用版本和存储格式：新增不兼容请求或修改传输语义时必须递增
`PROTOCOL_VERSION`，无需迁移本地书库。

两端都参与时才会走正文通道，旧版本因此不会收到不认识的请求（见第 7.9 节）。

拒绝时 `ok=false` 并带上 **`code`**（`proto::HandshakeCode`）：`protocol_mismatch` /
`group_mismatch` / `not_trusted` / `removed_by_peer` / `busy` / `auth_failed` /
`unexpected_message`。码属于线协议的一部分 —— 两端各自按码出文案，界面据此给出可操作引导：
客户端把码落成 `error::Code`，错误串形如 `group_mismatch|两台设备不在同一同步群组`，
App 侧再翻成当前语言（`src/lib/sync.ts` 的 `syncErrorText`）。`message` 仍带一句中文提示，
只用于日志与排障；旧对端不带 `code` 时按提示文本处理（`#[serde(default)]`）。

`port_c` 是客户端**自己同步服务的监听端口**（`0` = 没在监听）。服务端据此把对端地址记成
「**来源 IP + `port_c`**」，下次才能主动连回来。**不能拿这条连接的源端口当地址**：
它是内核临时分配的，连接一断就回收，拿它当对端地址会让下一次连接直接被拒
（`ECONNREFUSED`）。对端声明 `0` 时服务端会**清掉**它的旧地址，而不是留着一个死地址反复重试。
来源 IP 是通配地址（`0.0.0.0` / `::`）时同样不记：那不是能连的地址，界面上会被当成
「本机地址」展示、用户照着填必然失败；引擎启动时还会清掉历史数据里这类地址
（`SyncEngine::forget_unusable_peer_addrs`）。记下对端之后服务端会回调宿主
（`ServerOptions::with_peer_seen`），App 借此推一次状态事件，界面立刻刷新设备列表。

同步页「本机地址」由 `src-tauri/src/sync/lan.rs` 现取网卡地址：同步服务监听在
`0.0.0.0:47821`，而 `0.0.0.0` 只是「所有网卡」的绑定意图、不是能连的地址，
所以界面列的是真实地址（跳过回环 / 未指定 / IPv6 链路本地，最像局域网的排最前）。

- 请求：`Pull{since, limit}` / `Push{ops}` / `Stat` / `Ping`，以及正文通道的
  `ContentIndex{books}` / `ChapterDigests{book}` / `PushChapters{book, items}` /
  `PullChapters{book, cids}`（第 7.9 节）与资源通道的 `AssetIndex{books}` /
  `AssetDigests{book}` / `ExchangeAssets{book, push, pull}`（第 7.10 节）；
- 分帧：`[u32 大端长度][JSON]`，握手阶段上限 64 KiB、业务帧 8 MiB；
- 发现：UDP **查询 / 应答**（`net::discovery`），广播报文同样带 HMAC，
  **只回应本群组的查询**——陌生设备连「这里有一台 ReaderX」都探不到；
  同一台设备从多个网卡应答时优先记住回环地址。
- 握手还会查一次**本机拒绝接入的名单**（`device.json` 的 `removed_devices`，界面上「删除设备」
  的结果）：名单里的设备在群组校验之后就被拒（`removed_by_peer`，提示里给「重新接受」的入口），
  一条数据都不收。
  名单读的是引擎的当前状态，所以删除 / 重新接受都不需要重启监听端。
  它是**本机单方面**的名单：对端不知情，也不会因此丢掉它手里的数据（见第 7.4 节）。

**安全边界（明确取舍）**：信任单位是「群组密钥」（配对码）。
持有配对码即可同步该群组数据；**载荷不加密**（局域网内视为同一信任域），
设备名与实体数据对同网段的被动监听者可见。需要更强保护时应换 AEAD / TLS，
而不是在这里加字段。凭据（密钥）永不进日志。

## 6. 独立命令行运行器

不启动 App 也能在两台机器上跑通（`--features cli`）：

```bash
# 设备 A（手机）
readerx-sync --data-dir /data/a init --name 手机
readerx-sync --data-dir /data/a pairing            # 把配对码抄到设备 B
readerx-sync --data-dir /data/a create book --set 'title=三体' --set 'tags=["科幻"]'

# 设备 B（桌面机）
readerx-sync --data-dir /data/b init --name 台式机 --join '<配对码>'
readerx-sync --data-dir /data/b serve              # 前台运行（Ctrl+C 退出）

# 回到设备 A：发现并同步
readerx-sync --data-dir /data/a discover
readerx-sync --data-dir /data/a sync auto
readerx-sync --data-dir /data/a conflicts          # 看冲突队列
readerx-sync --data-dir /data/a resolve <id> --keep local|remote
```

其余命令：`status` / `ls` / `show` / `ops` / `set` / `unset` / `incr` /
`add` / `rm` / `move` / `delete` / `restore` / `remove-peer` / `accept-peer` /
`ls-assets` / `get-asset`（后两个看资源暂存区里对端发来的封面 / 插图）；
`--json` 输出机器可读结果，`--verbose` 把日志打到标准错误。
完整用法见 `readerx-sync --help`。

> `remove-peer <设备id>` 与 App 里的「删除设备」是同一件事（设备 id 可以用前缀，`status`
> 会列出已知对端与已移除设备）：本机不再与它同步，并拒绝它连进来；`accept-peer <设备id>`
> 解除拒绝（要立刻同步一次再 `sync <地址>`）。两个命令与 App 交替使用没有问题 ——
> 名单就写在 `device.json` 里。

## 7. App 侧是怎么接的

引擎、网络、桥接与界面各管一段，改哪一层就只看哪一层：

```text
src-tauri/crates/readerx-sync/   引擎（本文件第 2~6 节）
src-tauri/src/sync/
  settings.rs    设备本地设置（开关 / 自动同步 / 落地游标），与 device.json 分开放
  identity.rs    跨设备身份：同一本书在两台设备上算出同一个实体 id
  bridge.rs      本地数据 ↔ 引擎实体（发布本地改动 / 落地远端结果）
  lan.rs         本机对外的局域网地址（同步页「本机地址」，见第 5 节）
  service.rs     引擎与网络的生命周期、自动同步线程、事件推送
  commands.rs    readerx_sync_* 这些 Tauri command（含 `readerx_sync_lan_addrs`）
src/lib/sync.ts                  前端接线：状态 signal + 事件 + 缓存重载
src/pages/Sync.tsx               设置 → 同步（开关 / 配对 / 设备 / 自动同步 / 冲突入口）
src/pages/SyncConflicts.tsx      冲突裁决
```

### 7.1 同步什么

| 数据 | 同步 | 说明 |
| --- | --- | --- |
| 书籍元信息 | ✅ | 书名 / 作者 / 简介 / 标签 / 分组 / 格式 / 文件名 / 字节数 / 来源地址 |
| 阅读时长 | ✅ | 按独立来源保存不可变累计快照，逐项取最大值再求和；重复同步不重复计数，见 [阅读时长统计](reading-time.md) |
| 阅读进度 | ✅ | 章节 + 章内字符偏移 + 上下文快照（`LwwSilent`，见第 2 节） |
| 书签 | ✅ | 位置（不可变）+ 备注（可改） |
| 分组 | ✅ | 以**分组名**为身份 |
| 书源 | ✅ | 以**书源地址**为身份；整份 JSON 按多值处理（两边都改就进冲突队列） |
| 书源分组 | ✅ | 以**分组名**为身份；书源的归属记在书源实体的 `group` 字段上，见第 7.12 节 |
| 文本替换规则 | ✅ | 以**规则内容**为身份（作用域 + 书 + 查找 + 替换 + 是否正则），见第 7.7 节 |
| 分章规则 | ✅ | 用户自定义的章节标题正则，以**名称 + 正则**为身份 |
| 书籍结构 | ✅ | 每本书的章节目录（cid / 标题 / 地址），一本书一份、整份 LWW，见第 7.8 节 |
| 书籍正文 | ✅ | 按章指纹对账 + 按需搬运，**不进操作日志**，见第 7.9 节 |
| 封面 | ✅ | 字节走**资源通道**（不进操作日志），本机仍是 `bookdetail.json` 里的一段 data URL，见第 7.10 节 |
| 章节插图 | ✅ | 同上；插图还要设备无关的文件名，见第 7.11 节 |
| 未下载的插图 | ✅ | 正文里的引用会同步过去，字节由资源通道按引用补齐（两轮到位） |
| 导入时间 / 色相 | ❌ | 每台设备各自生成的，同步过去只会制造无意义的差异 |
| 书籍 ID | ✅ | 书库与同步实体统一使用稳定的 `b-<16 位十六进制>` ID |
| 分组 / 书源 / 规则 ID | ✅ | 本地记录、同步实体与归属引用使用同一 ID |
| 登录态 / Cookie | ❌ | 凭据不进同步（与 `readerx-source` 的边界一致） |
| 界面偏好（主题 / 字号 / 侧边栏…） | ❌ | 手机与桌面的偏好本来就该各调各的 |

### 7.2 跨设备身份（`identity.rs`）

App 书库、书源、书架分组、书源分组及规则与同步使用同一套 ID。首次创建按下表派生，接收端直接
使用实体 ID 保存。本地不再为同步数据另建随机 ID；书籍、书源和分组已有 ID 在编辑后沿用，规则仍按内容派生：

| 对象 | 身份依据 |
| --- | --- |
| 在线书 | 书源地址 + 书籍详情页地址 |
| 导入书 | 文件名（大小写归一）+ 字节数 |
| 分组（书架） | 分组名 |
| 书源分组 | 分组名（与书架分组是两个命名空间，同名不互通） |
| 书源 | 书源地址 |
| 文本替换规则 | 作用域 + 书实体 id + 查找 + 替换 + 是否正则 |
| 分章规则 | 规则名称 + 正则 |

代价是明确的：改名 / 换一份同名不同内容的文件会被当成新书（各自收敛，只是不互相同步），
而算内容哈希要把整本书读一遍，导入路径上不可接受。

升级时在界面与同步线程启动前迁移旧 `local-*` 书籍目录、元信息、书签归属、阅读进度、
按书替换规则、旧阅读时长键及听书缓存目录；恢复旧备份后也执行迁移。正文和图片引用
原样保留，已有同步实体、操作历史及墓碑不重建。迁移待办先写盘，中断后继续执行。
遇到重复同步身份或状态键冲突时保留原数据并返回错误，避免覆盖用户数据。

同一启动阶段还迁移书源、两类分组及规则 ID，更新 `bookdetail.json` 的
`bookSourceId` / `groupId` 和书源的 `groupId`。书源 ID 同时用于源文件、同步实体与
在线书关联；新同步载荷携带 `book_source_id`，旧载荷保留按地址查找的兼容路径。
登录态 `source_sessions/` 与 CLI 登录配置 `profiles/` 跟随书源 ID 搬迁。
待办包含完整元信息和引用，写完全部新文件后才删除旧文件；启动与旧备份导入均可重跑。
同地址但内容不同的重复书源、冲突登录态会停止迁移并保留原文件。

### 7.3 数据流

```text
本地写入（导入 / 改元信息 / 翻页 / 加书签 / 改分组 / 改书源 / 改书源分组 / 改替换与分章规则）
  → 命令层钩子 → bridge::publish_*  → 引擎（值与引擎相同时一条操作都不写）
一次同步结束
  → bridge::materialize → 写回本地文件 → 事件 readerx-sync-applied
  → 前端重载对应缓存（书架分组 → 书库 → 进度 → 书签 → 书源分组 → 书源 → 文本替换 → 分章规则）
```

三条容易踩的坑都已经在桥接层处理掉：**值没变不产生操作**（否则每次启动都灌一屏日志）、
**待裁决的字段不再自动改写**（否则用户还没裁决就被"自动解决"）、
**重新导入同一个文件不覆盖同步来的元信息**（以引擎为准落地回来）。

### 7.4 开关与后台行为

- **「关闭同步」≠「不记账」**：只要启用过一次（`settings.json` 的 `activated`），
  本地改动就持续记进操作日志，关掉的只是网络与自动同步；重新打开后一起同步出去。
  **从未启用过的用户完全不付这份代价**（不建引擎、不写日志）。
- 首次启用会把现有书库灌进引擎（几百本书 = 几百条 fsync 的操作），因此这一步在
  **后台线程**做：开关本身立刻响应。
- 同步服务（TCP 监听 + UDP 发现）与自动同步线程都在启用后常驻，退出时 `shutdown()`。
- **配对是显式动作**：手动「同步」只与**已配对设备**（成功同步过、记在 `peers.json` 里的那些）
  同步，不会扫局域网找设备；扫描只在两处发生 —— 用户点「查找局域网设备」，以及刚填完配对码时
  找一次对方。扫描结果里不认识的设备**永不自动同步**。
- **删除设备**：设备列表里每台已配对设备都能删除（`readerx_sync_remove_peer`；界面上先点一次
  进入确认态，再点才真删）。删除做三件事：从 `peers.json` 里删掉它（地址、同步计数、
  「对方已知版本」一起删 → 自动同步与「立即同步」都不会再找它）、把它写进拒绝名单
  （`device.json` 的 `removed_devices`，握手阶段生效）、丢掉它那批还等不到前序的缓冲操作。
  **已经同步进来的数据保留**：那是两台设备共同的历史，按来源回滚会把数据改坏；
  对端也不会收到通知。撤销删除**只有显式动作**：在「查找局域网设备」里对这台设备点「重新接受」
  （扫描结果里它带「已删除」标记）—— 先撤销拒绝（`readerx_sync_accept_peer`）、再与它同步一次，
  它才回到设备列表。自动同步与手动同步都**不撤销**删除：否则「设备正在同步时点了删除」这种
  时序会让会话结束时的记录把删除悄悄抹掉。
  一台设备主动连「删过它的」设备会拿到 `设备已被对端移除`（数据一条都不收），这是预期行为：
  被删的一方只能等对方重新接受。删过之后「连接设备」区会提示还有几台被删除的设备
  （`SyncStatus.removedPeers`），免得它们看起来「凭空消失」、也没人知道去哪恢复。
- **自动同步的节奏**：成功 → 按设置的间隔（默认 15 分钟，1/5/15/30/60 可选）带随机抖动；
  还没有已配对设备 → 安静等待（不打日志、不占 CPU）；有已配对设备但都没连上 →
  15 秒起翻倍退避（最多到一个间隔），并顺手用一次发现**刷新已配对设备的新地址**
  （DHCP 换 IP 很常见，但只更新已知设备的地址，不与陌生人同步）。
- 自动同步默认只由**设备 id 较大**的一方发起，避免重复双向传输；
  连续几轮没人成功时另一侧也会主动起来。

### 7.5 已知取舍（App 侧）

- **「删除设备」只挡住本机这一侧**：拒绝名单是本机单方面的，对端仍持有它那份数据与群组密钥
  （也不会收到通知）。要两边都断，得在对方设备上也删掉本机；反过来，被删的一方从那台设备
  同步不进来，但它自己那份数据不受影响。
- **对端删书会删掉本机那一份**：删除按墓碑同步，本地文件（含正文、书签、听书缓存）
  一并删除。这是「同步」应有的语义，但确实比"只同步元信息"更有破坏性。
- **操作日志只增不减**：每翻一页会写一条进度操作，长期使用后 `oplog.jsonl` 会持续增长
  （第 8 节的已知取舍，需要时引入快照传输模式压缩）。
- **配对码就是凭据**：与设备身份同放在 `<同步目录>/device.json`，持有它即可同步该群组。
- 冲突页的裁决只有「保留本机 / 采用对端 / 忽略」三种；要手填值可以裁决后到书籍详情页改。
- **网络等待不占引擎锁**：一条连接传完整个差集，每个接收包实时落库；
  停止或失败时保存已接收的数据再断开连接。
- **暂存正文只等「能建书」**：本机缺对应书源（在线书）、或元信息还没同步过来时，
  正文会留在 `<同步目录>/content/` 里不落地（不会自动过期，也不会被当成垃圾清理）。
- **同一章两边内容不同按设备 id 定胜负**：不做内容级合并（正文不是可自动合并的数据），
  指纹不同时整个换掉。改一章正文的最坏情况是「以另一台设备那份为准」。

### 7.7 规则类数据（文本替换 / 分章规则）

两类规则都是「**内容即身份**」：实体 id 由规则内容派生，因此不需要额外记账 ——
两台设备各自添加同一条规则会收敛成同一条；改规则内容等于删旧建新，不会出现
「一条规则带着两边的半份内容」。规则字段在 schema 里是不可变（`Frozen`）的，
写入永远来自创建而不是改写。

- **文本替换**（`readerx.textReplacements`）：`global` 规则对所有书生效；
  `book` 规则按**书实体 id** 走，与迁移后的本地书籍 ID 一致。
  - 书被删除会**级联**删掉它的规则（全局规则没有 `book_id`，不受影响）。
  - 本机还没导入的书：它的规则留在引擎里**不落地**（本地清单里看不到），
    书落到本机时再补一次；同理，本机发布规则时**不会**把这类规则当成
    「用户删掉了」而入墓碑 —— 否则一次本地发布就会抹掉对端为那本书建的规则。
- **分章规则**（`readerx.chapterRules`）：内置规则是代码常量、不进状态文件，
  参与同步的只有用户自定义的那些；显示顺序按创建时间、其次实体 id，
  两台设备看到同一个顺序。

### 7.8 书籍结构（章节目录）

一本书的目录（章节 cid / 标题 / 来源地址）是**正文的派生数据**，单独成一份
`book_structure` 实体，实体 id 跟书身份绑定（`bs-<书实体 id>`），删书时级联删除。

- **为什么整份目录是一个 LWW 值**：逐章拆成实体的话，一次目录刷新（在线书换目录、
  重新导入换了分章方式）要为几千章写几千条 fsync 操作，而目录本身没有细粒度合并的
  价值 —— 它就是「这本书现在有哪些章」的整份快照。代价是两边并发改目录时 LWW 选边、
  败方进冲突队列（正文不受影响，正文由内容通道单独对账）。
- **目录里不带字数**：`chars` 是正文的派生值，对端落地后字数仍由它自己的正文算出来
  （没有正文的章节就是 0）。带过去只会在两端口径不完全一致时反复触发「目录变了」的重写。
- **发布时机**：整本书写入（导入 / 在线书重新拉目录）时直接取内存里的章节头；
  启动对账时只扫 `content.json` 的章节头，**不解析正文、不统计字数**。
- **落地时机**：只对**本机已有的书**落地，且**按 cid 复用原有正文**（改标题 / 换地址 /
  增删章都不会把已经下载的正文弄丢）；本机还没有这本书时目录先留在引擎里 ——
  光有目录的书打开是空白，等正文到了（内容通道）再连目录一起建书。
- 目录变了会同时触发一次书架元信息刷新（章节头），落地事件里带上
  `chapters`（本机书 id 列表），前端据此丢掉这几本的正文缓存。

### 7.9 正文通道（`readerx-sync` 的 `content` 模块）

正文（书籍正文）走**单独一条通道**，不进操作日志、不进实体快照：那是「一行一条 JSON、
每次 flush 整份重写」的存储，一本几百 MB 的书会让日志与快照各膨胀一份，每翻一页还要
重写一遍。正文只借用版本向量的**思路**：两边各算一份「有哪些章、指纹是什么」，差集就是
要搬的东西。

```text
本机：ContentSource（App 读 books/<id>/content.json 的章节指纹缓存 digest.json）
    + 暂存区（<同步目录>/content/<书实体 id>/，对端刚发来、还没落地）
一次会话：逐本比总览 → 不一样的书比逐章指纹 → 推「对端没有的」、拉「本机没有的」
落地：宿主在下一次 materialize 里把暂存正文写进书库（必要时按元信息新建这本书）
```

- **按需分块**：一批正文不超过 4 MiB / 100 章（协议帧上限 8 MiB），单章超过 4 MiB 的
  会报告未完成（图片以 data URL 塞进正文的旧数据会命中这条）。会话没有总量预算，
  在同一条连接上连续传输；App 收到完整数据包后实时落库。
- **指纹只算正文**（段落 + 规范化 JSON 的结构化块，见 `body_fingerprint`）：标题 / 地址
  属于目录（结构）实体，改标题不该触发一次正文重传；对象键序差异不算不同内容。
- **同一章两边都有但指纹不同**时按**设备 id 大的一方**为准：无论谁发起、谁先谁后，
  收敛到同一份内容，不会你推我我推你。
- **能力协商**：握手时各自自报是否参与正文同步（`Hello.content`，缺字段的旧对端 = false）。
  对端没有正文来源（旧版本 / CLI）时直接跳过这条通道 —— 既不向它发未知请求
  （旧版本会当协议错误断连接），也不会把正文搬到它那里去。
- **落地即建书**：本机还没有这本书时按引擎里的元信息 + 目录 + 暂存正文新建一本
  （`bookdetail.json` + `content.json`）。两种情况**暂不建书**、正文继续留在暂存区：
  元信息还没同步过来、在线书的本机没有对应书源（书身份含书源地址，缺了会建成同步不到的
  孤儿）。PDF 与其他导入书一样，根据解析后的文字块 / 页面图片建书。封面与插图走资源通道
  （第 7.10 节）单独搬，不阻塞建书；封面还没到时底色由书实体 id 派生。
- **落地后清暂存**：写盘成功才删暂存文件（写失败留着下次再试）；重复推送同样的内容
  按「没有变化」处理并清掉暂存。对端删书时，它还没落地的正文一起丢掉。
- **目录是顺序的权威**：建书 / 落地目录时按结构实体排章节顺序，暂存正文按 cid 填进去；
  没有结构实体时按 cid 排序（结构还没到就只按正文建书，下次目录到了再对齐顺序）。

- 正文总览请求点名所有有效书实体，即使本机还没有任何正文；空设备主动同步也能取回对端的书籍。

### 7.10 资源通道（`readerx-sync` 的 `assets` 模块）

封面与章节插图是**二进制资源**：它们既不属于操作日志（一行一条 JSON，每次 flush 整份重写），
也不适合塞进正文（一张图会让一章的指纹变来变去）。因此另开一条与正文同构的通道：
**指纹对账 + 按需搬运**，字节不落任何 JSON 账本，只在暂存区与书库之间走一趟。

```text
本机：ContentSource::assets / ::names —— 「这本书引用了哪些资源、我手里有哪些」
    （封面来自书籍元信息，插图来自图片目录；指纹 = sha256(字节)）
    + 暂存区（<同步目录>/assets/<书实体 id>/，对端刚发来、还没落地）
一次会话：逐本比总览 → 不一样的书比逐个资源的指纹 → 缺什么搬什么
落地：宿主在下一次 materialize 里写进书库（见第 7.1 节的两行说明）
```

- **名字是设备无关的**：插图叫 `sha256(图片地址) 前 40 位 hex + 扩展名`，封面固定叫 `cover`。
  名字同时出现在**正文块**（引用）与资源通道（内容）里，落地时不需要在两张表之间翻译；
  本机书 id 不进名字 —— 否则两台设备对同一段正文算出两个指纹，正文通道会一直误判「不一样」。
- **内容即身份**：指纹是**字节**的 sha256，不是地址的哈希。同一个名字下内容不同
  （换过封面 / 同一个地址换了图）时按规则裁决，判据是内容而不是「谁先谁后」。
- **方向规则（关键）**：
  - **封面**是可改的数据：两边都有且指纹不同时，**设备 id 大的一方**为准；只有一边有时，
    「有」的一方推给「没有」的一方 —— 换了设备不会凭空丢封面。
  - **插图**随章节引用补齐：正文赢家可以补图，另一侧明确引用但缺失的图也会双向传输。
    刚收到的暂存正文引用同样参与对账，因此新设备同一轮就能收到扫描 PDF 的页面图。
    全局设备 id 只裁决同章正文冲突，不能阻止另一侧独有章节的图片传输。
- **只推缺失的插图**：对端已经有这个指纹就不再搬（重复推送按「没有变化」处理并清掉暂存）。
  换了设备后的第一次同步因此只搬真正的差集；同一连接持续搬完大书库，按包实时落库。
- **能力协商**：`Hello.content` 决定是否参与资源同步；新增 `Hello.asset_chunks` 表示
  支持超大资源分片（缺字段默认为 false）。小资源继续使用原交换请求；需分片时，
  对端若没有该能力会提示更新两端应用，不发送旧构建无法识别的请求。协议版本与
  软件版本不变，新增能力不改变原有合并规则。
- **暂存区的粒度是「书的实体 id + 类别 + 名字」**：`assets/<书实体 id>/<类别:名字 的 sha256>.json`，
  内容就是一份序列化后的资源（字节编 base64）。落地成功才删暂存文件，写失败留着下次再试；
  对端删书时，它还没落地的资源一起丢掉。
- **封面就是一段 data URL**：同步不改变本机的存储形态 —— 本机 `bookdetail.json` 里的
  `cover` 还是 data URL，界面那一侧一个字节都不用动。因此封面资源会额外带上**原文**
  （`dataUrl`），落地时原样写回；只用「字节 + MIME」拼回来，只要差一个字符就会被当成
  「封面又变了」而反复写盘。封面不参与实体（操作日志）里的 `cover` 字段，那个字段仍然
  不同步：一段几十 KB 的 base64 写进「一行一条 JSON、每次 flush 整份重写」的存储，
  一本一本攒起来会把操作日志与实体快照一起撑大。
- **对账要点名每一本书**：对端只回应答里点过名的书，而封面恰恰是「本机一本资源都没有、
  却要对端推过来」的情形，因此请求里的名册带全（`AssetIndex.books`），另一份
  `known` 只列「本机算过且有资源」的书，供对端省掉重复计算。只报「我有资源的书」的话，
  新设备的封面永远同步不过来。
- **CLI 只能看暂存的那一侧**：`ls-assets [<书实体 id>]` 列出收下的资源，
  `get-asset <书实体 id> <名字> [--out <文件>]` 把字节导出来核对。CLI 没有书库
  （不注册 `ContentSource`），因此它既不会推也不会落地 —— 这是刻意的：**落地的语义属于宿主**。

### 7.11 章节插图：引用名与本地文件名的归一

插图比封面多一层麻烦：**它的名字写在正文块里**（`ChapterBlock.local` / 段内图的
`local`），而正文块要跨设备比对指纹。因此插图的名字必须**设备无关**：

```text
资源名 = sha1(图片地址) + 扩展名          ← 同步通道与正文引用用的是同一个字符串
本地文件 = <应用数据目录>/images/<资源名>   ← 文件名就是资源名，不再带本机书 id
```

- **为什么用 sha1 而不是别的**：同步引入前落盘的文件名是 `<本机书 id>_<sha1(地址)>.<ext>`，
  哈希部分本来就是 sha1 —— 归一只需剥掉前缀，旧数据不用重新下载，改名即可。
- **归一发生在读取与落地两处**：`book_images::normalize_image_refs` 在书籍读取（`get_book`
  的图片自愈）与同步落地（`bridge::apply_staged_assets`）时就地改名并把正文块里的引用换成
  资源名。**旧文件不在也要归一**（对端引用了一张本机还没下载的图是常事）：名字才是给对端
  看的，字节由资源通道补。
- **不归一就会被正文通道反复重传**：本机书 id 进名字 → 两台设备对同一段正文算出两个指纹
  → 每次同步都认为「两边不一样」。
- **插图与正文同轮补齐**：资源清单包含已经落地的引用和刚收到的暂存正文引用。
  只有本地文件名的扫描页图片也能按归一资源名对账；传输不设会话总量限制。
- **方向规则**：正文赢家可以补图，明确引用但缺失的图也双向补齐（见第 7.10 节）。封面按
  「有推给没有、都有则设备 id 大者为准」，谁发起都会补齐。
- **删除按引用**：名字归一之后不能再按「文件名前缀 = 本机书 id」扫目录（一张图还可能被
  两本书同时引用），`delete_book` 因此按这本书**引用到的名字**删，归一名还要确认没有别的书
  引用它 —— 宁可留下几个孤儿文件，也不删掉别人正在用的图。

### 7.12 书源分组（`readerx.sourceGroups`）

书源分组（管理页 / 发现页的筛选条那一层）由两部分组成，**两边都同步**：

- **分组清单**：使用 `source_group` 实体，首次按名称派生 `sg-<哈希>`，与书架分组
  不共命名空间。本地清单直接保存实体 ID；改名继续更新同一实体，对端删组后移除。
- **书源的归属**：`book_source` 的独立 `group` 字段和源文件的 `groupId` 使用同一
  书源分组 ID。归属不塞进 `MultiValue` 的整份书源 JSON，避免换分组与改 JS 相互覆盖。
  对应分组不存在时按未分组落地。

`readerx.sourceGroups` 的写入钩子发布清单并重发布组内书源；分组改名保留 ID，
归属没变时不产生重复操作。
删除分组时（`readerx_source_group_clear`）Rust 还会把组内书源的 `groupId` 清掉并
**重新发布这几份书源** —— 那条路径不经过清单写入，光靠上面的重发布看不到归属的变化。

## 8. 覆盖的场景与已知边界

已实现并有测试覆盖：并发改不同实体 / 不同字段、同字段同值、同字段异值（LWW + 留档）、
集合增删（add-wins / remove-wins）、计数器并发、列表并发插入与移动、
删除 vs 更新（`DeleteWins` / `UpdateWins` / `Manual`）、双方都删、删除后恢复、
不可变字段改写、唯一键冲突、级联删除（级联 / 阻止 / 孤儿）、乱序到达（因果缓冲）、
重复提交（op_id 去重）、时钟不准与回拨（HLC）、schema 版本较新（缓冲）、
多租户隔离（群组）、断点续传（版本向量）、中继（A→B→C）、跨进程写者冲突（目录锁）、
移除设备（拒绝接入 / 重启后保持 / 重新接受）；规则类数据（文本替换 / 分章规则）与
章节目录的收敛；正文通道的能力协商（旧对端跳过）、指纹对账、按章搬运与暂存落地；
资源通道的封面搬运与冲突收敛、插图跟随正文赢家、能力协商与暂存区去重；
书源分组与书源归属的双向收敛（新增 / 换组 / 删组退回未分组）。

**明确的边界**（不要指望框架做这些）：

- **富文本协同编辑**：需要 Yjs / Automerge 这类 CRDT；这里只提供有序列表的
  位置键方案（重复插到最前会在用尽首位空间后退化为「追加到末尾」，见 `order.rs`）。
- **强一致业务**（金额、库存、权限）：P2P 没有权威方，这类数据应走服务端事务或单写者
  设计，不要交给自动合并。
- **二进制大对象**：听书音频 / 书籍**原文件**（EPUB / PDF 文件本身）不在同步范围；
  同步的是「解析后的章节正文」（第 7.9 节）与「封面 / 章节插图」（第 7.10 节），
  PDF 导入时已经解析为文字块与页面图片，同步这些数据后可在对端直接阅读，包括扫描件。
- **端到端加密**：载荷不加密（见第 5 节）。
- **日志压缩**：操作日志只增不减（见第 4 节）；App 每翻一页都会写一条进度操作，
  长期使用需要引入快照传输模式。
- **网络变化触发同步**：App 目前只有手动与定时两种触发（见第 7.4 节），
  没有监听系统网络事件。

### 内置隐藏分组

隐藏分组不写入 `readerx.groups`，书籍的 `group` 字段使用固定身份 `__hidden__`。
发布与落地都单独识别这一身份，因此新设备建书、已有书移动与移出隐藏分组都保留正确归属，
不会创建一个同名的普通分组。旧版本漏发的隐藏归属在首次升级时于旧操作落地之前恢复，迁移标记写入同步设置，之后不再重复覆盖归属；
若两端的本地归属已经被旧同步覆盖，需要重新将书移入隐藏分组。

### 实时落库、进度与停止

手动、指定设备与定时同步都在同一条连接内传完整个差集，取消会话的 200 章 / 32 MiB
总量限制。单帧上限仍然保留；章节按帧大小分包，超大封面和插图按 512 KiB 分片传输，
单章正文超过预算仍会报告未完成，
不会假报成功或反复重连。引擎只在读取、合并与暂存时短暂持锁，网络等待不占锁。

接收端每个完整数据包经过校验与暂存后立即落库，成功后才确认推送或发送进度。
正文与图片暂存、书库文件采用写入后同步磁盘与原子替换；写盘失败保留暂存和原游标。
落库串行执行，操作游标仅推进到落库开始时已经存在的操作，避免并发到达的数据被漏掉。
连接或同步错误时，在释放连接之前再执行一次落库。未完整收到或尚未通过校验的报文
不计入已接收数据，下次同步会按差集重新传输。

停止按钮提交停止请求后显示正在保存。传输线程处理完当前请求、落库已接收数据后才
关闭连接，不再连接下一台设备；等待中的网络请求受连接与读写超时限制（App 为 8 秒）。
停止是正常结束，不显示同步失败或完成提示；下一次同步从磁盘现状继续补齐差集。

`readerx-sync-progress` 报告当前设备、阶段、书名、书籍序号、当前书籍的通道完成数与总数、
累计发送 / 接收章数和图片数、传输字节数。正文与图片按真实差集显示进度；连接与元信息
使用不定进度条。状态查询带最近的快照，事件序号防止旧响应覆盖新进度。

回归覆盖：450 章书籍一条连接全部落地、接收中读取磁盘、停止后保存并补齐、对端中途
断线后保存并补齐、纯图片 PDF、独有章节双向补图与隐藏分组归属迁移。

### 暂存资源与在线书的恢复

资源先到、正文或对应书源尚未到时，封面和插图保留在暂存区。落地前先检查本机书籍，
不存在时不读取、解码图片，也不反复输出逐书资源等待日志。
一次正文落地只读取一次书源库，读取失败按落地错误处理，不再当作书源缺失。
旧同步书籍缺失或携带过时的 `source_url` 时，以本机书源地址和书籍地址重算书籍 uid，
只有与原实体 uid 一致才恢复关联；不能仅凭域名或书源名称猜测。
拥有本机书籍的设备在对账时会补齐实体缺失的书源地址与统一书源 ID，不覆盖远端书名等编辑。
正文与资源对账连续查询缺失书籍时，书库索引最多每秒重建一次；刚落地的新书最迟在下一次
重建时可见，未收到的资源仍由暂存区保留并在后续落地重试。

### 推送确认与重复数据

接收端的 `stored` 仅表示本次新写入的正文或资源数量。并发同步、重试时，相同数据
可能已经进入暂存区，接收端会跳过重复写盘。发起端收到少于发送数量的确认时，会
重新请求该书的指纹清单，逐项核对发送内容；指纹一致仍计为传输完成，缺失或指纹
不一致则报错。此复核沿用已有协议请求，不需要修改存储格式或迁移数据。

资源无法读取时，错误包含书实体 id 和资源名；错误和日志不包含正文、图片字节或凭据。

### 超大封面与插图的分片传输

原资源批次预算 3 MiB 仅用于普通交换，不再限制一份资源的总大小。单份图片超过预算，
或封面的 `bytes_b64` 与原文 `dataUrl` 编码后超过预算时，改用 `PushAssetChunk` /
`PullAssetChunk`，每片最多 512 KiB。整份资源先序列化再切片，接收端按偏移重组，
校验总长度、完整 SHA-256 指纹和资源名后才送入原有 `assets/` 暂存与落库流程；
图片字节、MIME、扩展名和封面原文均原样保留。小资源仍沿用 `ExchangeAssets`。

拉取首片时固定资源快照，后续片段从同一份数据读取，避免每片反复读文件或混入变化。
分片进度逐片上报并执行检查点；一份资源仅在最后一片被完整确认后计为完成。

每条连接的接收片段放在 `<同步目录>/asset-transfers/<会话随机 id>/`，各连接独立，
不进入对账清单或书库。完整重组后立即删除分片文件，正常完成、取消或断线时清理
会话目录；异常退出的遗留目录在下次取得独占目录锁后清理。既有已完成资源的格式
保持不变，无需迁移数据。重新连接会重发未完整校验的资源，已完成的资源按指纹跳过。

仅升级一端时普通资源仍兼容；传输超大资源需要双方都支持 `asset_chunks`。
